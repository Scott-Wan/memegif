# GIF 选段循环预览设计

**日期：** 2026-07-23  
**状态：** 已确认

## 1. 背景与根因

当前项目通过 Python、pywebview 和原生 HTML/CSS/JavaScript 提供视频/GIF 选段、画面裁切和 GIF 导出能力。

普通视频使用 `<video>` 播放，并在时间滑块或数字输入变化后设置 `currentTime`。GIF 则通过 `<img>` 加载完整的 base64 data URL。`<img>` 不提供按时间定位能力，而且当前 `seekTo()` 在 GIF 模式下直接返回。因此：

- `state.startSec` 和 `state.endSec` 会正常更新；
- 最终转换会按所选起止时间精确截取；
- 但 GIF 预览仍始终循环完整源文件，不会反映选段。

这不是时间状态同步失败，而是现有 GIF 预览媒介不支持 seek 的能力缺口。

## 2. 目标

导入 GIF 后：

1. 调整起止时间时，播放窗口立即响应；
2. 预览只播放 `[startSec, endSec]` 所选区间；
3. 播放到终点后自动回到起点并继续播放；
4. 拖动滑块期间保持实时反馈；
5. 使用轻量预览质量，最终导出仍基于原始 GIF；
6. 保持普通视频、裁切和最终转换的现有行为不变。

## 3. 非目标

本次不做以下工作：

- 不在每次滑块变化时重新生成 GIF；
- 不在前端实现完整 GIF 帧解码器；
- 不修改最终 GIF 的预设、调色板、体积回退或输出命名；
- 不做与该问题无关的界面或架构重构。

## 4. 方案比较

### 4.1 导入时生成轻量视频预览（采用）

导入 GIF 时使用 ffmpeg 一次性生成临时 MP4，此后通过 `<video>` 的 `currentTime` 和播放事件控制区间循环。

优点：

- 拖动期间无需重复转码，响应接近即时；
- 可复用项目已有的本地 Range HTTP 服务和视频 seek 逻辑；
- 区间播放语义清晰，改动范围可控。

代价：

- 首次导入需要短暂预处理；
- 需要管理预览缓存和临时文件。

### 4.2 每次时间变化生成裁剪 GIF（不采用）

即使增加防抖，拖动期间仍会频繁启动 ffmpeg，容易出现延迟、资源竞争和旧请求覆盖新结果，不满足实时预览目标。

### 4.3 前端解码 GIF 并用 Canvas 播放（不采用）

需要引入解码器并处理逐帧延时、disposal、透明度和缓存，复杂度及内存成本显著高于本项目需求。

## 5. 架构设计

### 5.1 预览媒体生成

在 `converter.py` 新增独立的轻量预览生成函数：

- 输入：源 GIF 路径和目标临时 MP4 路径；
- 输出：生成后的文件信息或目标路径；
- 保持原始宽高比；
- 最长边上限固定为 640 像素，帧率上限固定为 24fps；
- 使用 H.264、YUV420P、`faststart` MP4，并采用偏向速度的编码参数；
- 对含透明像素的 GIF，仅在预览 MP4 中合成到与编辑区一致的深色背景；原始 GIF 和最终导出不受影响；
- 不应用用户的画面裁切或最终导出预设。

该函数只负责媒体转换，不管理缓存、URL 或 UI 状态，便于独立测试。

### 5.2 应用 API 与缓存

在 `app.py` 增加 GIF 预览准备接口：

1. 校验源文件存在且为 GIF；
2. 根据规范化源路径及文件状态查找本次运行缓存；
3. 缓存未命中时，在应用专属临时目录中生成 MP4；
4. 通过现有媒体注册表登记生成文件；
5. 返回现有本地 HTTP 服务可访问的 URL；
6. 转码或注册失败时返回可读错误。

缓存键必须包含足以识别源文件变化的信息，至少包括规范化路径、文件大小和最后修改时间，避免同一路径文件被替换后继续使用旧预览。

同一源 GIF 在一次程序运行内只生成一次有效预览。并发请求同一资源时，应避免多个 ffmpeg 进程重复生成同一目标文件。

### 5.3 临时目录生命周期

- 应用启动时创建本次运行专属的系统临时目录；
- 所有轻量预览文件均写入该目录；
- 更换文件时允许保留已生成文件，以支持本次运行内复用；
- 窗口关闭或进程正常退出时统一清理目录；
- 异常退出留下的系统临时文件不影响下次运行，因为每次使用独立目录。

### 5.4 前端媒体状态

`state.kind` 继续表示源文件类型，不能因为 GIF 使用 `<video>` 预览而改成 `video`。前端需要把以下概念分开：

- **源类型：** 决定最终处理逻辑和失败降级；
- **当前预览元素：** 决定 seek、尺寸读取和裁切遮罩布局。

GIF 轻量预览成功后，当前预览元素为 `<video>`；失败降级后为 `<img>`。`mediaEl()` 和 `mediaSize()` 应根据实际预览模式判断，而不是只依赖源类型。

### 5.5 导入流程

导入 GIF 时：

1. 保存路径、时长、帧率和源类型；
2. 初始化全选区间；
3. 显示“正在准备片段预览…”；
4. 请求后端生成或读取轻量预览；
5. 请求成功后将 URL 加载到 `<video>`；
6. 媒体就绪后从当前 `startSec` 开始播放；
7. 根据当前起止值进行区间循环。

为每次导入分配递增的请求序号。异步响应返回时，只有序号和当前源路径均匹配的响应才能更新预览，防止快速换文件时旧响应覆盖新文件。

普通视频仍直接使用现有 `video_src()` 流程，不进行额外转码。

## 6. 区间播放规则

`state.startSec/endSec` 继续作为唯一时间真相。

### 6.1 修改起点

滑块或数字框提交新起点后：

- 先通过 `setRange()` 完成钳制和必要的起止交换；
- 若当前预览可 seek，则定位到最终 `state.startSec`；
- 继续或恢复播放。

### 6.2 修改终点

提交新终点后：

- 先通过 `setRange()` 得到最终区间；
- 为保持实时编辑反馈，起点或终点变化后统一从最终 `state.startSec` 开始播放；
- 若媒体仍在等待加载，则记录区间，待 `loadeddata` 后从起点播放。

### 6.3 播放循环

监听 `<video>` 的播放时间事件：

- 当前时间达到或略微超过 `endSec` 时，将 `currentTime` 设置为 `startSec`；
- 若媒体仍应播放，则调用 `play()`；
- 比较时使用与浏览器事件频率相匹配的小容差，防止越过终点；
- 当区间过短或无效时暂停，不进入高频 seek 循环。

该区间约束也可用于普通视频，使两种源类型的预览语义一致，但不得破坏现有视频 seek 行为。

## 7. 裁切兼容

GIF 轻量 MP4 与原 GIF 保持相同宽高比，因此裁切框仍可通过显示坐标映射到源媒体真实坐标。

为了避免预览缩放尺寸被误当成源尺寸：

- 裁切换算应使用源媒体的真实宽高，或确保按比例映射时使用与源图一致的宽高比；
- 不能直接把轻量 MP4 的缩小像素尺寸当作最终源 GIF 尺寸；
- GIF 降级到 `<img>` 后仍沿用原图 `naturalWidth/naturalHeight`。

为确保裁切导出区域精确，`load_video()` 增加源媒体 `width` 和 `height`，前端存入独立状态并用于 `currentCropPixels()` 换算；轻量预览自身的 `videoWidth/videoHeight` 只用于界面布局。

## 8. 错误处理与降级

### 8.1 预览生成失败

- 恢复现有 `<img>` base64 GIF 整段预览；
- 显示：“无法生成选段预览，最终转换仍会按所选时间生效”；
- 时间选段、画面裁切和最终转换保持可用。

### 8.2 预览媒体加载失败

- 清理 `<video>` 的失败来源；
- 切换回 `<img>`；
- 使用同样的降级提示；
- 不修改原始路径或所选区间。

### 8.3 快速切换文件

旧请求不得：

- 修改当前 `<video>` 或 `<img>` 来源；
- 覆盖当前状态提示；
- 重置当前时间区间或裁切状态。

### 8.4 过短区间

沿用最终转换对过短片段的限制。预览层检测到区间短到无法稳定循环时暂停并显示当前帧，避免高频 seek 和 `play()` 调用。

## 9. 测试设计

### 9.1 转换层测试

为轻量预览函数增加自动化测试：

- 给定有效 GIF 能生成非空 MP4；
- 输出最长边不超过预览上限；
- 保持原始宽高比；
- 输出时长接近源 GIF 时长；
- 输出像素格式和编码可被预期播放器支持；
- 输入不存在或 ffmpeg 失败时抛出明确异常。

测试素材应为仓库内体积较小、具有多个不同画面的 GIF，以便验证时间变化确实对应不同内容。

### 9.2 API 与缓存测试

- GIF 预览接口成功返回本地 HTTP URL；
- 相同源文件的重复请求复用同一个生成结果；
- 源文件大小或修改时间变化后缓存失效；
- 并发请求不会重复生成或暴露未完成文件；
- 非 GIF、缺失文件和转码异常返回结构化错误；
- 临时目录位于系统临时位置并能在退出清理。

### 9.3 前端逻辑测试

若引入轻量的 JavaScript 测试环境，应将区间判断提取为可测试的小函数，覆盖：

- 修改起点后定位到新起点；
- 播放达到终点后回到起点；
- 缩短终点且当前位置越界时立即回到起点；
- 起止交换后使用 `setRange()` 的最终值；
- 过短区间不会进入循环抖动；
- 旧导入请求不会覆盖新请求；
- GIF 预览成功时使用 `<video>`，失败时使用 `<img>`；
- 普通视频现有定位行为不受影响。

如果仓库暂不引入 JS 测试工具，则至少在 Python 测试中覆盖预览生成/API，并按下述实际验收清单验证前端。

### 9.4 实际验收

1. 导入 GIF，等待一次轻量预览准备完成；
2. 拖动起点，画面立即跳到新起点并从该处播放；
3. 拖动终点，播放只在新区间内循环；
4. 使用数字时间输入，行为与滑块一致；
5. 连续快速拖动时，不重复转码、不卡在旧区间；
6. 开启裁切，裁切框位置和最终导出区域一致；
7. 快速导入另一个文件，旧预览不会覆盖新文件；
8. 模拟预览生成失败，仍能看到原 GIF 并完成选段导出；
9. 导入普通视频，现有预览、seek、裁切和转换正常；
10. 最终 GIF 仍从原始文件生成，质量和体积回退行为不变。

## 10. 预计改动范围

- `converter.py`：增加轻量 GIF 到 MP4 的预览生成函数；
- `app.py`：增加预览临时目录、缓存、并发保护、API、URL 注册和退出清理；
- `web/main.js`：分离源类型与预览元素，实现异步请求保护、区间循环和降级；
- `web/index.html`：仅在播放属性确有需要时调整 `<video>`；
- `tests/`：增加预览生成、缓存/API 和可行的前端逻辑测试；
- `README.md`：删除“GIF 预览不支持 seek”的旧限制，说明支持所选片段循环预览。

## 11. 成功标准

本设计完成后，GIF 导入仅在首次准备预览时发生一次轻量转码。此后无论通过滑块还是数字输入调整起止时间，播放窗口都会实时反映并循环所选片段；最终导出仍基于原始 GIF 和原始质量，普通视频及裁切功能无回归。
